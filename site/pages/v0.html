CS2 Tactical Intelligence · Version 0

Early-Round Site Outcome Forecaster

V0 asks a deliberately narrow question: given the observable state of a Mirage T-side round, can we predict whether the round will eventually produce an A plant, B plant, or no plant?

The purpose of V0 is not to recommend strategy yet. It is to first prove that useful tactical prediction is possible.

1. Why Start With Prediction?

The long-term system is intended to move through several levels: 

OBSERVE
↓
UNDERSTAND
↓
PREDICT
↓
RETRIEVE
↓
OPPONENT MODEL
↓
EVALUATE
↓
RECOMMEND

Jumping directly to strategy recommendation would mix together several unsolved problems. V0 therefore freezes the first measurable prediction task.

2. Frozen V0 Task

For an eligible T-side Mirage round, observe the game state at:

  • 10 seconds after freeze_end
  • 20 seconds
  • 30 seconds
  • 40 seconds

Predict: 

P(A_PLANT)
P(B_PLANT)
P(NO_PLANT)

An observation is excluded if the bomb has already been planted or the round has already ended. This prevents the model from seeing information that occurs after the event it is supposed to predict.

3. Why Match-Level Cross Validation?

Each round can generate several observations. For example, the same round may appear at 10s, 20s, 30s and 40s.

A random observation split could therefore place part of one round in training and another part of the same round in testing.

Even a round-level split can leak team and match-specific tactical patterns across rounds.

V0 therefore groups the entire demo file as one unit: 

Group = demo_filename

One match
→ entirely TRAIN
or
→ entirely TEST

All model comparisons reuse the same frozen five grouped folds. This makes ablation comparisons paired and interpretable.

4. Dataset

  • 20 Mirage demos
  • 444 parsed rounds
  • 443 valid-timing rounds
  • 1 partial opening round excluded
  • 1,268 eligible observations
  • 0 missing feature values

Observation counts: 

10s → 442
20s → 373
30s → 270
40s → 183

Later horizons contain fewer observations because rounds that already planted or ended are no longer eligible. Therefore cross-horizon performance is not a comparison over an identical cohort.

5. Data Validation Changed the Design

Bomb-site label audit

The obvious implementation was to use the round-level bomb_site field from the parser.

Manual validation showed that this field was incorrect for the initial demo. Planted rounds were being reported as B even when the actual plant event occurred at A.

V0 therefore reconstructs the label from bomb plant events: 

BombsiteA → A_PLANT
BombsiteB → B_PLANT
No plant → NO_PLANT

This became an important project rule: upstream parser fields are not automatically treated as ground truth.

Bomb-state reconstruction

A second issue was determining the current bomb position. Using only the latest bomb event fails when the bomb has been dropped and subsequently picked up.

The final policy became: 

If exactly one T currently carries C4:
    use the current carrier position
else:
    use the latest valid bomb-drop event

Validation on the original 49 observations produced: 

35 carried
14 dropped
0 suspicious

6. Feature Design

Features were not selected by blindly exposing every parser column. Each family started from a tactical question.

A1 — Offensive Geometry

Question: Where is the attacking team and what shape is its formation?

Features include:

  • T centroid
  • team stretch
  • x/y range
  • mean pairwise distance
  • convex hull area
  • bomb position
  • bomb-to-team-centroid distance

Centroid alone cannot distinguish between a tightly grouped team and a widely spread formation with the same average position. Spread-related features were therefore added to represent formation shape.

A2 — Motion

Movement features are derived from position history rather than parser-specific velocity fields.

This preserves training-serving parity for future live adapters.

A3 — Combat

Geometry sanity checks exposed an ambiguity. Several observations had zero spread or zero convex-hull area.

The implementation was not broken. Those observations often had only one surviving T player.

This showed that geometry requires survival context. Combat features were therefore added:

  • T / CT alive count
  • health totals and differences
  • armor totals and differences

A4 — Economy

The hypothesis was that current equipment value could represent remaining combat capability.

It was tested rather than assumed useful.

A5 — Defense and Interaction

The model was also given CT spatial structure and interaction features such as:

  • CT centroid
  • CT formation spread
  • T-to-CT centroid distance
  • minimum opponent distance
  • mean nearest-opponent distance

7. Why Numerical and Tactical Sanity Checks?

A feature can be mathematically valid and still represent the wrong game concept.

The pipeline therefore uses two checks before predictive evaluation: 

Feature implementation
↓
Numerical sanity
↓
Tactical sanity
↓
Predictive ablation

Numerical sanity checks completeness, invalid values and plausible scale.

Tactical sanity checks whether feature movement corresponds to observable game behavior.

These checks validate construction. They do not prove predictive usefulness. That requires held-out ablation.

9. Why Logistic Regression Was Not the End

Logistic Regression is intentionally simple. It is a strong baseline because the relationship between each feature and the prediction score is primarily linear.

But tactical behavior can contain interactions: 

T position
×
CT position
×
bomb location
×
survival
×
formation

The mixed Defense result suggested that useful defensive information might exist but require a nonlinear model.

This hypothesis led to XGBoost.

10. What Is XGBoost?

XGBoost is a gradient-boosted decision-tree model.

A decision tree divides the feature space through questions such as: 

Is bomb_x below a threshold?
        ↓

Is CT centroid_y above a threshold?
        ↓

Is T alive count <= 2?

A single shallow tree is limited. Gradient boosting builds many trees sequentially. 

Tree 1
↓
makes predictions and leaves errors

Tree 2
↓
focuses on improving the remaining error

Tree 3
↓
continues correcting the ensemble

...

Combined ensemble
↓
final probability prediction

This allows nonlinear relationships and feature interactions that a simple linear model cannot easily represent.

11. Why XGBoost Fits V0

V0 currently has:

  • tabular state features
  • a relatively small dataset
  • plausible nonlinear tactical interactions
  • a need for a strong non-neural baseline

XGBoost is therefore a natural next model before introducing sequence neural networks.

12. Our XGBoost Design

n_estimators      = 300
max_depth         = 3
learning_rate     = 0.03
min_child_weight  = 5

subsample         = 0.8
colsample_bytree  = 0.8

reg_alpha         = 0.5
reg_lambda        = 5.0

tree_method       = hist

The design intentionally uses shallow trees, a small learning rate, regularization and sampling.

The dataset contains only 20 matches and 1,268 observations. A highly flexible tree ensemble could easily memorize development patterns.

These parameters were used as a conservative nonlinear baseline. They were not selected through a large hyperparameter search over the same OOF results.

15. Calibration

A tactical probability model should not only choose the right class. Its confidence should also mean something.

XGB-A5 top-label Expected Calibration Error: 

ECE = 0.0454

Observed accuracy rose consistently with confidence: 

confidence ≥ 0.50 → 66.8%
confidence ≥ 0.60 → 72.7%
confidence ≥ 0.70 → 81.2%
confidence ≥ 0.80 → 88.6%
confidence ≥ 0.90 → 94.9%

The main weakness occurred in the 0.6–0.7 confidence bin: 

mean confidence = 64.6%
observed accuracy = 52.4%

V0 is reasonably calibrated as a research baseline, but it is not yet treated as deployment-calibrated.

16. What Does the Model Get Wrong?

The confusion matrix exposed an important pattern. 

A ↔ B site swaps:
67 errors

Plant ↔ No Plant:
404 errors

Therefore: 

85.8% of all errors
cross the Plant / No-Plant boundary

The main V0 bottleneck is not deciding between A and B. It is predicting whether the round will successfully produce a plant.

17. Hierarchical Investigation

The error structure suggested that the original three-class problem might contain two different tactical subproblems. 

State
  ↓
Will Plant?
  ├── No
  └── Yes
        ↓
     A or B?

Before redesigning the architecture, the existing XGB-A5 probabilities were analyzed conditionally.

Plant vs No Plant

Log Loss  0.5740
Accuracy  69.1%
F1        0.7066

A vs B given True Plant

Log Loss  0.4490
Accuracy  78.5%

This supports the hypothesis that plant occurrence is the harder current subproblem.

This is diagnostic evidence from the existing three-class model, not yet evidence that a separately trained hierarchical model is better.

18. Why Group Permutation Importance?

Tree models provide built-in importance measures, but highly related features can substitute for one another.

Instead of asking:

How often did the trees use one particular variable?

V0 asks:

How much does held-out performance degrade if an entire information family is destroyed?

Each feature family is permuted as one block while preserving relationships inside the family.

21. Match-Level Robustness

Aggregate metrics alone can hide whether an improvement is caused by only a few favorable matches.

XGB-A5 therefore was compared with Logistic-A3 separately on every held-out match. 

XGB-A5 better Log Loss: 13 / 20 matches
XGB-A5 better Brier:    13 / 20 matches

Median Δ Log Loss: -0.0285
Mean Δ Log Loss:   -0.0401

The negative median indicates that the aggregate improvement was not caused only by one extreme match.

However, seven matches still regressed. Cross-match tactical variability remains important.

24. V1 Hypothesis

V0 currently uses one three-class classifier: 

State
↓
A / B / No Plant

V0 evidence motivates a candidate hierarchical V1 architecture: 

State
↓
Plant feasibility
├── No
└── Yes
     ↓
   Site choice
   ├── A
   └── B

This is a hypothesis produced by V0 evidence. It has not yet been shown to outperform the V0 model.

25. Evaluation Freeze

XGB-A5 was selected using the current 20-match development dataset. Continuing to tune repeatedly against these same OOF results would make the reported performance increasingly optimistic.

V0 development evaluation is therefore frozen here. Future architecture changes should eventually be evaluated using additional untouched matches or an appropriately nested design.
